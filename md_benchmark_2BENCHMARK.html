Benchmark Suite for dist-m4ri

This directory contains quantum LDPC CSS parity-check matrices (.mtx) and Stim circuit-level fault-tolerance files (.stim) spanning code distances $d = 4$ to $d \le 34$. Detector Error Models (.dem) can be generated on the fly from the .stim circuits with dist_m4ri.py (noise is added to the noiseless templates with add_noise); since version 0.14.0, the binary reduces the full DEM of a circuit exactly (Section 3), so that its distance, the circuit-level distance, is found as fast as that of the DEM with the minority-basis detectors stripped.

dist_m4ri computes the distance of a code (classical, quantum CSS, subsystem, or non-CSS in Pauli form) or of a circuit (from its DEM): it finds light codewords, which bound the distance from above, and proves that no lighter ones exist, which bounds it from below; when the two bounds meet, the distance is certified. These files are also the inputs of the benchmarks of dist_m4ri on a 128-thread server, whose current results this file shows:

How to Read the Results

  • Distance of a code. A codeword is a set of errors (columns of the parity-check matrix $H$) which flips no check but changes the encoded information, and its weight is the number of errors in it; the distance $d$ is the smallest weight of a codeword. A quantum CSS code has two sectors, the $X$-type and the $Z$-type logical operators, with the distances $d_X$ and $d_Z$, and $d = \min(d_X, d_Z)$ (Section 1); dist_m4ri computes one sector at a time.
  • Distance of a circuit (the circuit-level distance). The fewest faults (error mechanisms of the circuit's detector error model) which cause an undetected logical error. A DEM is a matrix whose rows are the detectors (parities of measurement outcomes which are deterministic without errors) and whose columns are the error mechanisms, together with the logical observables that each error flips; the circuit distance is the distance of this matrix. It is often below the distance of the code, since a single fault in the syndrome-extraction circuit (e.g., a hook error, which spreads from an ancilla to several data qubits) can act like several data errors (Section 2.6).
  • RW (method=1). A randomized information-set search (RW stands for random window): each step eliminates the matrix with its columns in a random order (for a DEM, often a window of columns close in time) and reads off light codewords. A codeword of weight $w$ proves $d \le w$, an upper bound. RW never proves that no lighter codeword exists, and the time until it reaches the minimum weight is random: it changes from run to run (seed). RW stops after a number of steps (steps), at the first codeword of weight at most wmin, at the timeout, or, by default, when the lightest codewords have been found again often enough (min_hits); with min_hits=0 and a given number of steps, every run does the same work (fixed work).
  • CC (method=2). An exhaustive connected-cluster search: it grows clusters of connected columns, weight by weight, and provably finds every codeword of the minimum weight up to its weight limit wmax. If it finds none of weight at most $w$, this proves $d > w$, a certified lower bound. Its work up to a given weight is deterministic: it depends neither on the seed nor on the number of threads.
  • method=3 (the default). RW and CC run together, with the threads balanced between them: RW lowers the upper bound $d_{\max}$, CC raises the lower bound $d_{\min}$, and the run ends when they meet, which certifies the exact distance. A run stopped earlier (by a timeout, or by given steps and wmax) reports the bracket $[d_{\min}, d_{\max}]$.
  • Full and reduced DEM. The full DEM of a memory circuit has the detectors of both bases ($X$ and $Z$ checks): with two-qubit depolarizing noise, many errors flip detectors of both. The stripped DEM keeps only the detectors of the measured basis, and its distance is only a lower bound on the circuit distance. Since 0.14.0, dist_m4ri merges the equal columns of a DEM and drops the minority-basis detectors when it verifies that this is exact (drop=auto, the default), which reduces the full DEM to a much smaller matrix with the same distance (Section 3).
  • Threads, wall time, speedup. $p$ is the number of threads (threads=p, with nothrottle=1 in the scaling runs, so that the binary uses all $p$ threads). The wall time is that of the whole run of the binary: it includes reading the input and, for a DEM, merging and reducing it (the input stage). The fast cases were repeated, and the figures show the medians. The speedup is $T(1)/T(p)$, the time on one thread over the time on $p$ threads, of the same version; the ideal speedup is $p$. Rates such as RW steps per second (Figure 9) use the RW time reported by the binary instead, without the input stage.
  • The default thread throttle. Without nothrottle=1, the binary may run RW on fewer threads than given: for example, on a large matrix whose dense RW working copies take more than 15 MB per thread, at most 32 threads run RW (the memory bus saturates at 32–64 threads), and a short run gets about one RW thread per 10 steps ($\lceil\texttt{steps}/10\rceil$).
  • The sparse elimination (since 0.17.0). On wide DEMs, with many more columns than detectors, an RW step eliminates with an $m \times m$ inverse per thread ($m$ detectors) instead of dense copies of the whole $m \times n$ matrix and of its transpose, which lifts the memory-bandwidth limit and removes the 32-thread dense-memory cap (Figures 4, 8, and 9).
  • The Python wrapper and reference values. dist_m4ri.py is the Python interface of the binary: it also builds the DEMs of Stim circuits and adds noise. All figures in this document measure the native dist_m4ri binary; for instances in Sections 1–2 and T3 whose dist_m4ri bracket remains open, known exact distances or tighter brackets from external exact certification or published constructions are noted as reference values.
  • The server. All runs used a two-socket AMD EPYC 7B13 server: 2 x 32 cores, i.e., 64 physical cores and 128 logical CPUs with SMT (two hardware threads per core), and 236 GiB of memory. In the thread-scaling runs (Figures 2–6 and 9), a run with $p$ threads is pinned with taskset to the logical CPUs $0..p-1$, in this order: 0–31 are the cores of socket 0, 32–63 those of socket 1, and 64–95 and 96–127 their SMT siblings (the second hardware threads of the cores of socket 0 and 1). Up to $p = 64$, each thread has a core of its own; beyond, the threads share cores. The gray line in the figures marks $p = 64$.
  • Versions. The figures compare versions of dist_m4ri, from 0.9.0 (pull request #26, 2026-09-18) to 0.17.5 (2026-11-27); dist_m4ri_old is the legacy single-threaded program, built from the 0.14.0 sources.

Methods

  • Hardware. One server, a virtual machine (KVM) with two AMD EPYC 7B13 sockets: 2 x 32 cores, 128 logical CPUs with SMT, and 236 GiB of memory; NUMA node 0 holds the CPUs 0–31 and 64–95, node 1 the CPUs 32–63 and 96–127.
  • Software. Each version of dist_m4ri named in a figure, built from its own sources with its makefile; dist_m4ri_old built from the 0.14.0 sources. The DEMs of the circuits are generated from the .stim files with dist_m4ri.py and stim 1.16 (Section 3).
  • Wall time. The time of the whole process: for Figures 1–8, from the binary's start to its exit, including reading the input and, for a DEM, merging and reducing it. Figure 9 shows rates per second of the RW time reported by the binary.
  • Exclusive runs. Within each benchmark, one run at a time. The runs of 0.17.5 (Figures 2–5, 7–9) and 0.17.3 (Figures 1 and 6) were made on a server without other jobs, with the load recorded; for the earlier runs, the load was not recorded.
  • Protocol of each figure:
    • Figure 1: method=3 with the default parameters on 128 threads (nothrottle=1, timeout=1800); 5 seeds (3 or 2 where a run exceeds 300 or 900 s).
    • Figures 2–5: fixed work (RW steps with min_hits=0, CC up to wmax, or both); $p = 1, \dots, 128$ threads on the CPUs $0..p-1$, with nothrottle=1; no time limit (timeout=0), except 600 s per case and method for 0.9.0 (400 s on the full DEM of Figure 5, also for 0.12.2); the same seed for every version; the median of three runs for the fast cases, one run otherwise.
    • Figure 6: long-running CC up to wmax (method=2, fixed work) and exact certification (method=3, default parameters, timeout=0); $p = 1, \dots, 128$ threads on the CPUs $0..p-1$ (p >= 4 for gross method=3), with nothrottle=1; median of three runs where $\le 150$ s, one run otherwise.
    • Figure 7: until a codeword of weight $d$ (wmin=d, min_hits=0, steps=10^9); 128 threads, not pinned, with nothrottle=1; a time limit of 300 s (120 s for gross); five seeds for 0.17.5 and 0.14.x (seven for gross), one run for 0.12.2 and 0.9.0.
    • Figure 8: the lightest codeword found against time; the default threads (32 RW threads on the two DEMs in 0.14.x, 128 in 0.17.5 via sparse elimination, and 128 on the codes), not pinned; until weight 18 (time limit 180 s) or 23 (240 s) on the DEMs, and 30 s on the codes; three seeds (two for bb_360).
    • Figure 9: RW with a fixed step limit; $p = 1, \dots, 128$ threads on the CPUs $0..p-1$, with nothrottle=1 and with the default throttle; a time limit of 25–30 s; one run per point.

Figure 1: Exact certification on 128 threads

Wall time to certify the exact distance (method=3) of 12 circuits and 13 CSS codes on 128 threads; 0.17.3, 2026-11-24.

Thread Scaling with Fixed Work and Certification

Figure 2: Gross code, RW with fixed work

Wall time of 3,000,000 RW steps on one sector of the gross code $[[144, 12, 12]]$ against the number of threads; versions 0.9.0–0.17.5, run 2026-10-11 to 2026-11-27.

  • Run: method=1 steps=3000000 min_hits=0 on css/gross_144_12_12_Hx.mtx with _Hz.mtx, for $p = 1, \dots, 128$. With min_hits=0, RW does not stop when it has found the distance, so every run does the same work: the time measures how fast the RW steps run, not how fast the distance is found (Figures 7 and 8 measure that).
  • Axes: left, the wall time against $p$ (both axes logarithmic); right, the speedup $T(1)/T(p)$ of each version, with the ideal speedup $p$ dotted. The star is the legacy single-threaded dist_m4ri_old (one thread).
  • Reading: with perfect scaling, the time halves with each doubling of $p$.
  • Result: RW scales almost linearly up to 64 threads, and the SMT siblings ($p > 64$) add more: 0.17.5 takes 82.2 s on one thread, with a speedup of 53.2x at 64 threads (1.55 s) and 68.2x at 128 (1.21 s; 0.14.0: 50.5 s, 58.1x, and 79.8x).
  • Why newer versions appear slower per step: a fixed-step run of 0.15.2 or 0.17.5 takes ~1.5–1.6x longer than 0.12.2 or 0.14.0 because each step also scans pairs of non-pivot columns (added in 0.14.4; with pairs=0 rw_opt=0, 0.17.5 matches 0.14.0), which cuts the steps needed to find light codewords by 6–30x (Figures 7 and 8). The smaller ~5–8% extra cost of 0.17.5 over 0.15.2 is per-step rw_opt=0x01 bookkeeping (reduced-$L$ syndrome table and per-step candidate buffer, still active on quantum codes when $\mathcal{T}_3 = \emptyset$), plus single-run jitter on ~1 s runs at $p = 64..128$.
  • Not shown: CC up to weight 11 and the exact distance (method=2 wmax=11 and method=3), which take a fraction of a second with 0.14.0 and later and are dominated by the start-up of the threads (Figure 6 measures multi-second to multi-minute CC and method=3 runs); their times are in HISTORY.md.
  • Versions (run dates): 0.17.5 (2026-11-27), 0.15.2 (2026-10-28), and 0.14.0, 0.12.2, and 0.9.0 (2026-10-11).
  • Details: HISTORY.md, Section 4 and Section 12.4.

Directory Structure and Running the Suite

Directory Structure

  • classical/: MatrixMarket (.mtx) parity-check matrices (_H.mtx) of classical linear, Reed–Muller, BCH, and quasi-cyclic LDPC codes (including a full-rank $k = 0$ check matrix).
  • css/: MatrixMarket (.mtx) CSS parity-check matrices (_Hx.mtx, _Hz.mtx) and logical operator bases (_Lx.mtx, _Lz.mtx for the Mitten codes, including the yarn_* codes of arXiv:2607.28795, and for the 2bga_* codes; the seven Bicycle Race codes of Origins, item 5, also have logical operators of the minimum weight in .nz files, _wX.nz and _wZ.nz).
  • subsystem/: MatrixMarket (.mtx) static subsystem gauge sectors, hook-extended CSS matrices, unmerged identical-column matrices, and duplicate-entry coordinate test matrices (_H.mtx, _G.mtx, _L.mtx).
  • stabilizer/: MatrixMarket (.mtx) non-CSS quantum stabilizer codes in length-$3n$ Pauli-expanded form (_H.mtx, _G.mtx, _L.mtx, with exact quantum Pauli weight and $|\mathcal{T}_3| \ge n$).
  • dem/: Standalone Detector Error Models (.dem), detector-drop lists (.drop), and make_large_drop_dems.py for large $A \neq 0$ drop benchmarks.
  • stim_surface/: Rotated planar surface-code .stim memory circuits ($d = 3, 5, 7, 9, 11, 13$).
  • stim_color/: Color-code memory_xyz .stim circuits ($d = 3, 5, 7, 9$, cycling $X \to Y \to Z$ detectors).
  • stim_noise/: Specialized noise-model, gate-set, and high-$k$ ($k = 125 > 64$) .stim circuits (PAULI_CHANNEL_1/2, XZZX rotated basis, HERALDED_ERASE, MPP/MZZ).
  • stim_bb/: Unmodified Bivariate Bicycle (BB), Gross, and Double-Gross .stim circuits from external repositories.
  • stim_mitten/: Mitten code .stim circuits generated via quits with CircuitBuildOptions(get_all_detectors=True) (mitten_*), and from the published hook-free schedules of arXiv:2607.28795 with make_yarn_mitten_circuits.py (yarn_*).
  • stim_shyps/: Unmodified SHYPS code .stim circuits ($Z$-basis memory).
  • stim_2bga/: Unmodified .stim circuits of two two-block group-algebra (2BGA) codes (memory in both bases).
  • stim_torus/: 2D local torus Bivariate Bicycle .stim circuits (d = 14 to 17, noiseless templates).
  • manifest/: versioned certification benchmark manifest (manifest/certify_v1.json) and canonical DEM builder (manifest/make_inputs.py; harness in tools/bench/).
  • figures/: the figures of the Key Results: 128-thread certification and long-running CC/method=3 scaling (Section 12 of HISTORY.md), fixed-work scaling across versions (Sections 4 and 12.4), the time to a minimum-weight codeword in the full DEMs of the circuits (Sections 5, 8, and 12.4), the lightest codeword found against time with RW pairs and stages (Sections 8 and 12.4), and the RW scaling of the stages of 0.17.5 (Sections 11 and 12.4); made by scratch/bench_0.17.5/make_figures_0175.py and scratch/bench_fold/make_phase2_figures.py (not in the repository).
